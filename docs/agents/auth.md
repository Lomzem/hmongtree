# Authentication boundaries

Read this document when changing sign-in, session protection, or authenticated Convex calls.

Clerk owns email verification and session lifecycle. Its provider widgets own sign-in and sign-up; configure email verification codes and disable passwords in the Clerk dashboard. Keep the catch-all sign-in and sign-up routes: Clerk navigates through nested verification steps. OAuth can later be enabled in Clerk without replacing the session model.

The installed `svelte-clerk` adapter is community maintained. Check installed exports before copying documentation examples: this release exposes `withClerkHandler` and `useClerkContext`. The server hook verifies the session, the root server loader serializes Clerk's safe initial state, and the protected route checks the verified user identity. Client visibility never authorizes backend access.

`src/env.ts` declares the SvelteKit 3 environment variables. The configuration boundary validates the required Clerk keys and Convex URL with Effect Schema. Missing or invalid settings render a setup notice without initializing either provider. Never render private configuration or validation inputs in error messages.

The root layout creates one Convex client. The auth feature's `.svelte.ts` adapter connects Clerk's reactive context to Convex and requests the `convex` JWT template. Token refresh bypasses Clerk's token cache when Convex requests it. The workspace subscribes only after Convex confirms authentication; there is no polling or scheduled backend work.

Convex's authentication configuration uses `CLERK_JWT_ISSUER_DOMAIN` from the Convex deployment environment. Its unconfigured `.invalid` issuer deliberately accepts no real identity. Set the actual Clerk issuer before deploying the authenticated operation. Browser publishable configuration is insufficient to configure the backend verifier.

The workspace query independently verifies the backend identity. Expected failures remain typed Effect values internally. Only `convex/auth/boundary.ts` translates authentication failures to a thrown `ConvexError`; the lint configuration limits this exception to that file. Future mutations must abort the transaction through an explicit boundary when failure must roll back writes: returning an error value commits preceding writes.

Generated Convex files are committed SDK output. Regenerate them through `bunx convex dev` or `bunx convex codegen` after configuring the deployment. The initial credential-free scaffold was generated by the installed CLI's offline `--system-udfs --typecheck disable` path; it does not prove that a cloud deployment or JWT template exists. Prefer the normal supported commands after connecting the project.

Verification covers missing configuration and authenticated versus unauthenticated backend query behavior using `convex-test`. A real email-code round trip, refresh, sign-out, and backend JWT verification additionally require configured Clerk and Convex projects; local tests cannot establish those external settings.

## Local setup

Copy `.env.example` to ignored `.env.local`. Supply `PUBLIC_CLERK_PUBLISHABLE_KEY` and `CLERK_SECRET_KEY` from the Clerk application. Connect the Convex project with `bun run convex:dev`, which writes `CONVEX_DEPLOYMENT` and `PUBLIC_CONVEX_URL`. Set `CLERK_JWT_ISSUER_DOMAIN` in that Convex deployment to the Clerk issuer. Create the Clerk JWT template named `convex` from its Convex preset; retain its audience and standard claims. Run the development server after configuring these values.

The initial development setup was verified with Clerk's reserved `+clerk_test` email pattern and documented test verification code. It reached the protected workspace and loaded the authenticated Convex viewer. Test addresses suppress email delivery in development; this checks the integration, not a real inbox's deliverability. See [Clerk test emails](https://clerk.com/docs/guides/development/testing/test-emails-and-phones). Keep test mode confined to development.
